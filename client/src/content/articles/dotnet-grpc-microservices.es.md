Entre microservicios, el JSON sobre HTTP/1.1 tiene un coste: serialización verbosa, sin
contrato fuerte, una conexión por llamada. **gRPC** responde a este contexto preciso con
binario compacto sobre HTTP/2, un contrato compartido y código generado en ambos lados. En
.NET, la integración es de primera clase.

## El contrato .proto, fuente única de verdad

Todo parte de un fichero `.proto`: describe los mensajes y el servicio, independientemente
del lenguaje. Es **el** contrato. Ni el cliente ni el servidor lo escriben a mano. En él se
declara un `service Pricing` que expone una llamada `rpc GetQuote (QuoteRequest)` que
devuelve un `QuoteReply`, con cada campo numerado (`string sku = 1;`, `int32 quantity = 2;`).

Estos números son la clave de la compatibilidad ascendente: nunca se reutiliza uno.

En el lado .NET, se referencia este fichero en el `.csproj` mediante
`<Protobuf Include="pricing.proto" />`. El paquete `Grpc.Tools` genera entonces, en tiempo
de compilación, la clase base del servidor y el cliente tipado. Ningún DTO que copiar:

```csharp
// Generated by Grpc.Tools from pricing.proto, do not edit
public partial class QuoteRequest
{
    public string Sku { get; set; }
    public int Quantity { get; set; }
}
```

## Servidor y cliente tipados

El servidor deriva de la clase generada `Pricing.PricingBase` y redefine el método. Sin
routing que cablear, sin deserialización manual: se recibe un mensaje fuertemente tipado.

```csharp
public sealed class PricingService(IPriceBook book) : Pricing.PricingBase
{
    public override async Task<QuoteReply> GetQuote(
        QuoteRequest request, ServerCallContext context)
    {
        var unitPrice = await book.LookupAsync(request.Sku, context.CancellationToken);

        return new QuoteReply { UnitPriceCents = unitPrice * request.Quantity };
    }
}
```

En el lado llamante, tampoco se escribe un `HttpClient`. Se inyecta el cliente generado
mediante `AddGrpcClient`, y se le llama como a un método local:

```csharp
builder.Services.AddGrpcClient<Pricing.PricingClient>(options =>
    options.Address = new Uri("https://pricing:443"));
```

## El streaming, el argumento decisivo

HTTP/2 permite el **streaming** en ambos sentidos, un escenario que REST no cubre
nativamente. Un `stream` del lado servidor empuja resultados sobre la marcha; un `stream`
bidireccional abre un canal full-duplex, útil para telemetría o chat.

En el código, se escribe en un `IServerStreamWriter<T>` y el cliente itera con
`await foreach`, sin polling ni WebSocket que improvisar.

## gRPC contra REST: elegir con conocimiento de causa

gRPC no es universal. Binario compacto, contrato fuerte, streaming, baja latencia: sus
puntos fuertes lo convierten ante todo en una herramienta **interna**, de servicio a
servicio.

Sus límites son reales: un navegador no habla gRPC nativamente (hace falta gRPC-Web y un
proxy), el binario no es legible a simple vista, y la depuración requiere herramientas
dedicadas.

Para una API **pública** consumida por terceros, REST/JSON sigue siendo a menudo la opción
correcta. La guía de Microsoft compara ambos en la
[doc de gRPC para .NET](https://learn.microsoft.com/en-us/aspnet/core/grpc/).

> El reflejo sano: **REST en la fachada pública, gRPC por dentro**. El contrato .proto se
> convierte entonces en la frontera formal entre vuestros servicios, una frontera
> versionada y compartida, que el compilador verifica.
