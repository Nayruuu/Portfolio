Between microservices, JSON over HTTP/1.1 has a cost: verbose serialization, no strong
contract, one connection per call. **gRPC** answers this exact context with compact
binary over HTTP/2, a shared contract, and generated code on both sides. In .NET,
the integration is first-class.

## The .proto contract, single source of truth

Everything starts from a `.proto` file: it describes the messages and the service, independent of
language. It is **the** contract. Neither the client nor the server writes it by hand. It
declares a `service Pricing` exposing an `rpc GetQuote (QuoteRequest)` call that returns a
`QuoteReply`, each field being numbered (`string sku = 1;`, `int32 quantity = 2;`).

These numbers are the key to backward compatibility: you never reuse one.

On the .NET side, this file is referenced in the `.csproj` via `<Protobuf Include="pricing.proto" />`.
The `Grpc.Tools` package then generates, at compile time, the server base class and the
typed client. No DTO to copy by hand:

```csharp
// Generated by Grpc.Tools from pricing.proto, do not edit
public partial class QuoteRequest
{
    public string Sku { get; set; }
    public int Quantity { get; set; }
}
```

## Typed server and client

The server derives from the generated `Pricing.PricingBase` class and overrides the method. No
routing to wire up, no manual deserialization: you receive a strongly typed message.

```csharp
public sealed class PricingService(IPriceBook book) : Pricing.PricingBase
{
    public override async Task<QuoteReply> GetQuote(
        QuoteRequest request, ServerCallContext context)
    {
        var unitPrice = await book.LookupAsync(request.Sku, context.CancellationToken);

        return new QuoteReply { UnitPriceCents = unitPrice * request.Quantity };
    }
}
```

On the calling side, you don't write an `HttpClient` either. You inject the generated client via
`AddGrpcClient`, and call it like a local method:

```csharp
builder.Services.AddGrpcClient<Pricing.PricingClient>(options =>
    options.Address = new Uri("https://pricing:443"));
```

## Streaming, the decisive argument

HTTP/2 allows **streaming** in both directions, a scenario REST doesn't cover
natively. A server-side `stream` pushes results as they become available; a
bidirectional `stream` opens a full-duplex channel, useful for telemetry or chat.

On the code side, you write to an `IServerStreamWriter<T>` and the client iterates with
`await foreach`, with no polling or WebSocket to hack together.

## gRPC vs REST: choosing with full knowledge

gRPC isn't universal. Compact binary, strong contract, streaming, low latency: its
strengths make it above all an **internal** tool, for service-to-service communication.

Its limits are real: a browser doesn't speak gRPC natively (you need gRPC-Web and
a proxy), the binary isn't human-readable, and debugging requires dedicated tools.

For a **public** API consumed by third parties, REST/JSON often remains the right choice. The
Microsoft guide compares the two in the
[gRPC for .NET doc](https://learn.microsoft.com/en-us/aspnet/core/grpc/).

> The sound reflex: **REST at the public façade, gRPC on the inside**. The .proto contract
> then becomes the formal boundary between your services, a versioned and
> shared boundary, checked by the compiler.
