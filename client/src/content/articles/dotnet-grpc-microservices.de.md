Zwischen Microservices hat JSON über HTTP/1.1 einen Preis: umständliche Serialisierung,
kein starker Vertrag, eine Verbindung pro Aufruf. **gRPC** antwortet auf genau diesen
Kontext mit kompaktem Binärformat über HTTP/2, einem gemeinsamen Vertrag und generiertem
Code auf beiden Seiten. In .NET ist die Integration erstklassig.

## Der .proto-Vertrag, einzige Quelle der Wahrheit

Alles beginnt mit einer `.proto`-Datei: Sie beschreibt die Nachrichten und den Service,
unabhängig von der Sprache. Sie ist **der** Vertrag. Weder Client noch Server schreiben ihn
von Hand. Darin deklariert man einen `service Pricing` mit einem Aufruf
`rpc GetQuote (QuoteRequest)`, der eine `QuoteReply` zurückgibt; jedes Feld trägt eine
Nummer (`string sku = 1;`, `int32 quantity = 2;`).

Diese Nummern sind der Schlüssel zur Abwärtskompatibilität: Eine einmal vergebene Nummer
wird nie wiederverwendet.

Auf .NET-Seite referenziert man diese Datei in der `.csproj` über
`<Protobuf Include="pricing.proto" />`. Das Paket `Grpc.Tools` generiert dann beim
Kompilieren die Basisklasse für den Server und den typisierten Client. Kein DTO zum
Abtippen:

```csharp
// Generated by Grpc.Tools from pricing.proto, do not edit
public partial class QuoteRequest
{
    public string Sku { get; set; }
    public int Quantity { get; set; }
}
```

## Typisierter Server und Client

Der Server erbt von der generierten Klasse `Pricing.PricingBase` und überschreibt die
Methode. Kein Routing zu verdrahten, keine manuelle Deserialisierung: Man erhält eine stark
typisierte Nachricht.

```csharp
public sealed class PricingService(IPriceBook book) : Pricing.PricingBase
{
    public override async Task<QuoteReply> GetQuote(
        QuoteRequest request, ServerCallContext context)
    {
        var unitPrice = await book.LookupAsync(request.Sku, context.CancellationToken);

        return new QuoteReply { UnitPriceCents = unitPrice * request.Quantity };
    }
}
```

Auch auf der Aufruferseite schreibt man keinen `HttpClient`. Man injiziert den generierten
Client über `AddGrpcClient` und ruft ihn wie eine lokale Methode auf:

```csharp
builder.Services.AddGrpcClient<Pricing.PricingClient>(options =>
    options.Address = new Uri("https://pricing:443"));
```

## Streaming, das entscheidende Argument

HTTP/2 ermöglicht **Streaming** in beide Richtungen, ein Szenario, das REST nicht nativ
abdeckt. Ein serverseitiger `stream` liefert Ergebnisse fortlaufend; ein bidirektionaler
`stream` öffnet einen Full-Duplex-Kanal, nützlich für Telemetrie oder Chat.

Im Code schreibt man in einen `IServerStreamWriter<T>`, und der Client iteriert mit
`await foreach`, ohne Polling und ohne zusammengebastelte WebSockets.

## gRPC gegen REST: eine bewusste Wahl

gRPC ist nicht universell. Kompaktes Binärformat, starker Vertrag, Streaming, niedrige
Latenz: Diese Stärken machen es in erster Linie zu einem **internen** Werkzeug für die
Kommunikation von Service zu Service.

Seine Grenzen sind real: Ein Browser spricht gRPC nicht nativ (nötig sind gRPC-Web und ein
Proxy), das Binärformat ist nicht mit bloßem Auge lesbar, und das Debugging verlangt eigene
Werkzeuge.

Für eine **öffentliche** API, die von Dritten konsumiert wird, bleibt REST/JSON oft die
richtige Wahl. Der Leitfaden von Microsoft vergleicht beide in der
[gRPC-Dokumentation für .NET](https://learn.microsoft.com/en-us/aspnet/core/grpc/).

> Der gesunde Reflex: **REST als öffentliche Fassade, gRPC im Inneren**. Der .proto-Vertrag
> wird damit zur formalen Grenze zwischen Ihren Services, einer versionierten und geteilten
> Grenze, die der Compiler prüft.
